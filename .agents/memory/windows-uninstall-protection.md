---
name: Windows uninstall protection and Store packaging
description: MSIX package removal is controlled by Windows; direct installers can guard normal uninstall flows but cannot defeat an administrator.
---

Microsoft Store/MSIX distribution must preserve the Windows-managed package lifecycle; an app should not promise to veto package removal during an active session. A direct EXE/MSI channel can add a session-aware custom-uninstaller guard, but this remains a normal-path friction layer rather than absolute protection against administrators, offline removal, or recovery tools. The direct channel's uninstall entry can be wrapped by the installed app and hand the original Windows Installer command back after authorization. jpackage does not create a separate application-owned uninstaller by default: Control Panel executes the registry `UninstallString`, and an app-side wrapper is only available after the app has launched unless the WiX package is customized at build time. The owner has confirmed that MSIX is an active Microsoft Store distribution and should not be abandoned.

**Why:** Public FocusMe documentation and Reddit reports indicate that protected focus sessions can block ordinary uninstall/settings paths, while Windows and third-party administrative tools still provide escape routes. Microsoft Store policy also requires products not to compromise device security or functionality. Microsoft documents that Control Panel uses the uninstall registry values, and Oracle documents that jpackage's install-time customization requires overriding WiX resources such as `main.wxs` or `overrides.wxi`. The owner confirmed on 2026-10-15 that Microsoft Store MSIX remains an active distribution and must not be abandoned.

**How to apply:** Keep Store/MSIX and direct EXE/MSI as separate, supported distribution channels. Keep MSIX in Windows install/start/uninstall and SelectorProvider verification (W5/W9); do not change or remove its SelectorProvider workaround until W9 is run on Windows with the actual shipped JDK and MSIX package. Runtime package detection must exempt MSIX from quit gates, uninstaller-process blocking, and installer firewall rules. Direct-channel protection belongs on normal quit plus Nuclear Mode's common uninstaller process path; keep it optional, explicit, reversible, and fail-open during crashes. An active focus session may use the Session PIN for tray Quit, but permanent uninstall must use the Global PIN or wait for the session to end. If uninstall must show the wizard before a user ever launches the app, implement and test a WiX install-time custom action instead of relying only on registry rewriting.

**Runtime guard (added 2026-11-05):** an owner test showed a Standalone Block did not stop an uninstall: Windows ran `msiexec /x` directly ("Gathering required information"), no FocusFlow wizard appeared, and the app was removed. Cause: the only process-level uninstaller block lived inside Nuclear Mode's scan, so a Standalone Block alone had none, and the registry redirect to the wizard is a convenience that can be missing or ignored. `UninstallGuard` (started from `StartupBootstrap`) now watches for a `msiexec` client whose command line removes FocusFlow (`UninstallCommandMatcher`) whenever any protection is active, kills it first, and prompts after. Every route to an MSI uninstall ends in that client, so the guard does not depend on the registry. The wizard (separate JVM) tells the guard it already authorized a removal through `UninstallAuthorizationHandoff` (a 60 s file grant). A process that was allowed once is never killed later. `WindowsUninstallRegistration.ensureRegistered()` now logs its outcome to enforcement.log (`[UninstallRegistration]`), skips writes when already correct, and is refreshed every 60 s so a Windows Installer repair is healed. Known limits: it only runs while FocusFlow runs; it cannot read the command line of a higher-privilege installer unless FocusFlow is elevated or Nuclear Mode's blanket installer block is on; an install-time WiX launch condition (the build-time option above) is still the only way to cover removal while the app is not running, and needs W-checks on Windows before it is shipped. Windows checks for this change are in Security/tracker.md style: W-U1 start a Standalone Block, uninstall from Settings, confirm the installer is stopped and a notice appears; W-U2 same with Control Panel and `winget uninstall`; W-U3 with a Global PIN and Always-On, uninstall, enter the PIN, start the uninstall again within 30 s; W-U4 with no protection active the uninstall still works; W-U5 check enforcement.log for `uninstall entry status=`.

**Installer-level check (added 2026-11-06):** the runtime guard above did not hold up in an owner test on real Windows (cause not yet known; look for `[UninstallGuard]` and `[UninstallRegistration]` lines in `~/.focusflow/enforcement.log`). So the MSI/EXE themselves now ask the app. `packaging/windows/main.wxs` is JDK 19's jpackage template plus one custom action, `FfUninstallCheck`: a type-34 action sequenced `After="CostFinalize"` (before InstallInitialize, so a refusal changes nothing) on `REMOVE="ALL" AND NOT UPGRADINGPRODUCTCODE`. It runs `cmd.exe /d /c if exist "[INSTALLDIR]FocusFlow.exe" (start "" /wait "[INSTALLDIR]FocusFlow.exe" --uninstall-check & if errorlevel 42 if not errorlevel 43 exit /b 1) & exit /b 0`. `Main.kt` handles `--uninstall-check` first (`UninstallCheck.run()` then `exitProcess`): same read-only database setup, PIN prompts and Standalone/Nuclear rules as the wizard, minus the extra confirm dialog. Exit 42 = deny; anything else = allow, on purpose, so a missing exe, JVM failure or crash can never trap a broken install. Wizard and runtime guard write the 60 s `UninstallAuthorizationHandoff` file after a PIN, and the check honours it, so nobody is asked twice. Build: Compose 1.6.1 clears jpackage's resource dir and has no way to add to it, so `packageGuardedMsi/Exe` (build.gradle.kts, only with `-Pfocusflow.guardedInstaller=true`, which CI sets) run `jpackage` on Compose's app image with the same args plus `--resource-dir packaging/windows`, then replace Compose's installers in `build/compose/binaries/main/{exe,msi}`. They refuse to run on a JDK other than 19; on a JDK upgrade copy the new default `main.wxs` and re-apply the addition. `scripts/verify-installer-uninstall-check.ps1` (CI step) reads the MSI tables, byte-searches the EXE, and does a silent install and uninstall on the runner confirming Windows Installer ran the action and the app answered "allowed". Installs made before this version have no check; it arrives with the next install or upgrade. Limits: the check is friction, not a boundary (a public property such as `UPGRADINGPRODUCTCODE=1` on the msiexec command line, or editing or deleting the protection data, defeats it); Windows shows its own generic "installation ended prematurely" message after the app's explanation when a removal is refused. Verified without Windows: the cmd line against stand-in programs under Wine for exit codes 0/1/41/42/43/255, a missing exe, and spaces, parentheses and `&` in the install path; main.wxs against the WiX 3.14 schema; unit tests. NOT verified: a real jpackage/WiX build, and a real refused uninstall.

**Manual Windows checklist for the installer check** (CI cannot answer a dialog, so a refusal needs a human): W-I1 install the new build, start a Standalone Block, then quit FocusFlow from the tray is refused, so instead kill it from Task Manager and wait for the watchdog; uninstall from Settings and confirm the FocusFlow message appears and the app stays installed; W-I2 same from Control Panel and `winget uninstall FocusFlow`; W-I3 with a Global PIN and Always-On, uninstall, enter the PIN once, confirm the uninstall then proceeds without a second prompt; W-I4 no protection active: uninstall works; W-I5 rename or delete `FocusFlow.exe` in the install folder, then uninstall: it must still succeed (fail-open); W-I6 install a newer build over an older one during a Standalone Block: the upgrade must not be blocked; W-I7 check `enforcement.log` for `[UninstallCheck]` lines.

**When uninstall protection applies (updated 2026-11-06, owner intent: anyone can uninstall unless their protection is armed to fight or is fighting).** One rule set, `UninstallProtectionService.activeRequirements(Action.UNINSTALL)`, is shared by the installer check, the runtime guard, the wizard and Nuclear Mode's installer block. Standalone Block: either mode (start now for N hours, or a scheduled start/end window) refuses uninstall with no PIN; a scheduled window now counts from the moment it is created, not only after its start time (uninstall only; tray Quit still ignores a window that has not started). Focus session / Focus Launcher: Global PIN if set, otherwise refused outright. Always-On: Global PIN if set; with no Global PIN uninstall is now refused outright, like a session (tray Quit unchanged: no requirement). Nuclear Mode: Nuclear PIN if set, otherwise refused outright. A Global PIN alone protects nothing. Unreadable database: busy or locked refuses; other failures need the typed phrase. Out of scope on purpose, per the owner: force-uninstallers, Safe Mode, deleting the per-user install folder or its tasks, and public-property tricks on `msiexec`; a per-machine install (admin-only file changes) was offered and not wanted, because anyone who uses the app must be able to uninstall it when nothing is armed.
